# Задание 9. Чтение с реплик и консистентность

## 1. Исходные условия

Каждый шард кластера — replica set из трёх узлов: один PRIMARY и два SECONDARY (схема 2, задание 3).
Запись идёт только на PRIMARY, SECONDARY получают изменения асинхронно через oplog. Поэтому данные на SECONDARY
могут отставать от PRIMARY — это **задержка репликации** (replication lag). В нормальном режиме она меньше секунды,
но растёт при пиковой записи, перегрузке узла (горячий шард, задание 8), сетевых проблемах и обслуживании.

Чтение с SECONDARY разгружает PRIMARY и масштабирует чтение, но может вернуть устаревшие данные.
Для каждой операции нужно решить, допустимо ли это.

### 1.1. Механизмы MongoDB

| Механизм | Что делает |
|---|---|
| `readPreference: primary` | читать только с PRIMARY — всегда актуальные данные. Значение по умолчанию |
| `readPreference: secondaryPreferred` | читать с SECONDARY, если он доступен и подходит по задержке; иначе — с PRIMARY |
| `readPreference: nearest` | читать с узла с наименьшей сетевой задержкой, PRIMARY или SECONDARY |
| `maxStalenessSeconds` | не читать с SECONDARY, который отстаёт больше заданного числа секунд. **Минимальное значение — 90 с** (MongoDB не может точнее оценить отставание; меньшее значение отклоняется) |
| `readConcern: "local"` | вернуть данные узла как есть; на SECONDARY они могут быть ещё не подтверждены большинством |
| `readConcern: "majority"` | вернуть только данные, подтверждённые большинством узлов, — они не будут откачены при смене PRIMARY |
| Причинно-согласованная сессия (causal consistency) | в рамках сессии клиент гарантированно видит свои предыдущие записи (read-your-writes), даже читая с SECONDARY: узел ждёт, пока догонит время последней записи клиента |
| `writeConcern: { w: "majority" }` | запись подтверждается, когда её получило большинство узлов; нужна, чтобы чтение `majority` и причинные сессии работали без задержек |

Шард-ключи из задания 7: `orders` — `{ customer_id: "hashed" }`, `products` — `{ _id: "hashed" }`,
`carts` — `{ owner_id: "hashed" }`. Read preference передаётся через mongos и применяется к узлам шардов.

### 1.2. Классы допустимой задержки

Бизнес-требования к «свежести» данных задают три класса:

| Класс | Допустимая задержка | Как обеспечивается |
|---|---|---|
| **A. Строгая консистентность** | 0 — только актуальные данные | `readPreference: primary`; в транзакциях — `readConcern: "snapshot"` или `"majority"` |
| **B. Почти актуальные данные** | до 90 с (обычно меньше 1 с) | `readPreference: secondaryPreferred` + `maxStalenessSeconds: 90`; если пользователь только что сам что-то изменил — причинная сессия |
| **C. Аналитика и отчёты** | до 15 минут | `readPreference: secondary` (не нагружать PRIMARY вообще); в идеале — отдельный скрытый (hidden) узел для аналитики |

Почему 90 секунд, а не меньше: это минимальное значение `maxStalenessSeconds`, которое MongoDB умеет гарантировать.
В обычной работе реальная задержка — доли секунды, а 90 с — граница, после которой отставший SECONDARY
автоматически исключается из чтения. Операции, которым не подходят даже доли секунды отставания, идут на PRIMARY (класс A).

## 2. Коллекция `products`

**Частота обновлений.** Описания, атрибуты и категории меняются редко — несколько раз в день при работе
контент-менеджеров. Цены — реже раза в день, кроме распродаж. Остатки меняются при каждой покупке —
самое частое обновление, на пике сотни раз в секунду по популярным товарам.

**Профиль нагрузки.** Чтений на порядки больше, чем записей: каталог и карточки товаров — самые посещаемые страницы.

| Операция чтения | Узел | Read preference | Read concern | Допустимая задержка | Обоснование |
|---|---|---|---|---|---|
| Каталог: поиск по категории, фильтр по цене | **secondary** | `secondaryPreferred`, `maxStalenessSeconds: 90` | `local` | B, до 90 с | Самое частое чтение. Если новый товар появится в выдаче на минуту позже или цена обновится с задержкой, ничего не сломается: цена и наличие перепроверяются при оформлении заказа. Разгружает PRIMARY, на который идут списания остатков |
| Карточка товара: название, описание, атрибуты, цена | **secondary** | `secondaryPreferred`, `maxStalenessSeconds: 90` | `local` | B, до 90 с | Данные меняются редко. Устаревшее описание или цена на странице не приводят к ошибке продажи — заказ оформляется по цене, перечитанной с PRIMARY |
| Отображение наличия на карточке и в каталоге («в наличии», «осталось 3 шт.») | **secondary** | `secondaryPreferred`, `maxStalenessSeconds: 90` | `local` | B, до 90 с | Это информация для покупателя, а не резерв товара. Риск «показали в наличии, а товар закончился» закрывается на этапе заказа: списание условное и выполняется на PRIMARY. Читать остатки с PRIMARY при каждом показе — значит нагружать PRIMARY именно там, где идут списания |
| Проверка остатка и цены при оформлении заказа | **primary** | `primary` | `snapshot` (в транзакции) | A, 0 | Здесь решается, можно ли продать товар. Чтение с устаревшего SECONDARY — это прямой риск продать отсутствующий товар или по старой цене. Само списание делается условным обновлением `{ "stock.msk": { $gte: qty } }` на PRIMARY, поэтому даже при гонке остаток не уйдёт в минус |
| Чтение остатков складом и администратором (пополнение, инвентаризация, смена цены) | **primary** | `primary` | `majority` | A, 0 | Решения о закупке и цене принимаются по точным данным; запросов мало, PRIMARY они не нагружают |
| Аналитика: популярность категорий, оборачиваемость остатков | **secondary** | `secondary` | `local` | C, до 15 мин | Отчёты строятся по агрегатам и не требуют свежих данных. Тяжёлые агрегации не должны отнимать ресурсы у PRIMARY |

## 3. Коллекция `orders`

**Частота обновлений.** Заказ создаётся один раз, затем его статус меняется несколько раз за жизнь заказа
(created → paid → shipped → delivered) с интервалами от минут до дней. Записей мало относительно чтений, но каждая важна.

**Бизнес-риск.** Пользователь, который только что оплатил заказ и видит статус «не оплачен», может оплатить
повторно или обратиться в поддержку. Пользователь, который оформил заказ и не нашёл его в истории, решит,
что заказ потерян.

| Операция чтения | Узел | Read preference | Read concern | Допустимая задержка | Обоснование |
|---|---|---|---|---|---|
| Страница «Заказ оформлен» сразу после создания | **primary** | `primary` | `majority` | A, 0 | Read-your-writes: заказ только что записан и может ещё не дойти до SECONDARY. Пользователь должен увидеть свой заказ |
| Статус заказа (страница заказа, отслеживание) | **primary** | `primary` | `majority` | A, 0 | Устаревший статус — прямой бизнес-риск: повторная оплата, обращения в поддержку, неверная информация о доставке. Запрос адресный (`_id` + `customer_id`) и лёгкий, поэтому нагрузка на PRIMARY небольшая. `majority` гарантирует, что показанный статус не откатится при смене PRIMARY |
| История заказов пользователя (список) | **secondary** | `secondaryPreferred`, `maxStalenessSeconds: 90` | `majority`, в причинной сессии | B, до 90 с; свои новые заказы — 0 | Список заказов просматривают часто, а старые заказы почти не меняются. Чтобы только что оформленный заказ не пропал из списка, чтение идёт в причинной сессии пользователя: SECONDARY вернёт результат не раньше, чем догонит его последнюю запись. Статусы в списке носят справочный характер; актуальный статус — на странице заказа (с PRIMARY) |
| Проверки перед изменением заказа: оплата, отмена, возврат, идемпотентность платежа | **primary** | `primary` | `majority` (или `snapshot` в транзакции) | A, 0 | По результату чтения меняется состояние заказа и движутся деньги. Решение по устаревшему статусу — двойная оплата, отмена отправленного заказа |
| Служба поддержки: карточка заказа клиента | **primary** | `primary` | `majority` | A, 0 | Оператор отвечает клиенту и меняет заказ — нужен актуальный статус. Запросов мало |
| Аналитика: выручка, заказы по геозонам и категориям | **secondary** | `secondary` | `local` | C, до 15 мин | Агрегации по большим объёмам; минутная свежесть не нужна, нагружать PRIMARY нельзя |

## 4. Коллекция `carts`

**Частота обновлений.** Самая высокая частота изменений на одного пользователя: каждое добавление, удаление
и изменение количества — запись, и сразу после неё пользователь видит корзину. Плюс слияние корзин при входе
и отметка «заказана».

**Бизнес-риск.** Пользователь добавил товар, а корзина с SECONDARY показывает его отсутствие — товар «пропал»,
пользователь добавляет повторно и получает двойное количество. При слиянии по устаревшей гостевой корзине
теряются товары.

| Операция чтения | Узел | Read preference | Read concern | Допустимая задержка | Обоснование |
|---|---|---|---|---|---|
| Получение текущей корзины `{ owner_id, status: "active" }` | **primary** | `primary` | `local` | A, 0 | Корзину читают сразу после каждого изменения. Любое отставание пользователь видит как «товар пропал» или «удалённый товар вернулся». Запрос адресный по шард-ключу и лёгкий |
| Счётчик товаров в шапке сайта | **primary** | `primary` | `local` | A, 0 | Тот же документ корзины; счётчик должен совпадать с содержимым корзины. Отдельное чтение с SECONDARY дало бы расхождение «в шапке 2 товара, в корзине 3» |
| Слияние гостевой корзины в пользовательскую | **primary** | `primary` | `snapshot` (в транзакции) | A, 0 | Чтение гостевой корзины и запись в пользовательскую — одна транзакция. Чтение с SECONDARY могло бы пропустить последние добавленные товары |
| Чтение корзины при оформлении заказа | **primary** | `primary` | `snapshot` (в транзакции) | A, 0 | Состав заказа берётся из корзины — он должен в точности совпадать с тем, что видел пользователь |
| Аналитика брошенных корзин (рассылки, ремаркетинг) | **secondary** | `secondary` | `local` | C, до 15 мин | Корзины со статусом `abandoned` и давно не обновлявшиеся активные корзины анализируются пакетно; задержка в минуты не влияет на результат |

`readConcern: "local"` для корзины на PRIMARY выбран сознательно: корзина — данные с коротким сроком жизни,
откат последнего изменения при смене PRIMARY (редкое событие) менее критичен, чем задержка ответа.
Запись в корзину при этом идёт с `writeConcern: { w: "majority" }`, поэтому подтверждённые изменения не теряются.

| carts | Аналитика брошенных корзин | secondary | до 15 мин |

Итог по коллекциям:

- **products** — основная доля чтений идёт на SECONDARY. Товары читают намного чаще, чем меняют, а устаревшие
  на секунды цена и наличие безопасны, потому что окончательная проверка при заказе выполняется на PRIMARY.
- **orders** — всё, что влияет на деньги и статус заказа, читается с PRIMARY. На SECONDARY — только история
  заказов (с причинной сессией) и аналитика.
- **carts** — всё на PRIMARY: пользователь читает корзину сразу после изменения, и любое отставание заметно.
  Нагрузка при этом небольшая — каждое чтение адресное и затрагивает один документ.

## 6. Задержка репликации: мониторинг и защита

### 6.1. Пороги

| Задержка SECONDARY | Состояние | Действие |
|---|---|---|
| < 1 с | норма | — |
| 1–10 с | повышенная | наблюдение |
| > 10 с дольше 1 мин | предупреждение | алерт: найти причину (перегрузка PRIMARY, диск, сеть, горячий шард — задание 8) |
| > 90 с | критическое | SECONDARY автоматически исключается из чтений класса B (`maxStalenessSeconds: 90`); чтения уходят на другие SECONDARY или на PRIMARY |
| > 15 мин | авария | отставший узел не годится и для аналитики; при угрозе выхода за окно oplog — пересинхронизация узла |

Если отстали все SECONDARY шарда, `secondaryPreferred` с `maxStalenessSeconds` отправляет чтение на PRIMARY.
Приложение продолжает работать, но PRIMARY получает всю нагрузку чтения. Поэтому задержку нужно отслеживать
и устранять до того, как она достигнет 90 с.

Как смотреть задержку на узле шарда:

```javascript
rs.printSecondaryReplicationInfo()

// Отставание каждого SECONDARY от PRIMARY в секундах
const st = rs.status();
const primary = st.members.find(m => m.stateStr === "PRIMARY");
st.members.filter(m => m.stateStr === "SECONDARY")
  .map(m => ({ node: m.name, lagSec: (primary.optimeDate - m.optimeDate) / 1000 }))
```

Правило Prometheus (percona/mongodb_exporter, имя метрики зависит от версии экспортёра):

```yaml
- alert: MongoReplicationLag
  expr: mongodb_mongod_replset_member_replication_lag > 10
  for: 1m
  labels: { severity: warning }
```

### 6.2. Запись

Все записи в `orders`, `products` и `carts` выполняются с `writeConcern: { w: "majority" }`. Это условие
корректности чтений из таблиц выше:

- чтение `readConcern: "majority"` с PRIMARY не вернёт данные, которые потом откатятся;
- причинная сессия на SECONDARY быстро получает подтверждённое время записи и не ждёт лишнего;
- при отказе PRIMARY подтверждённые заказы и списания остатков не теряются.

## 7. Настройка в приложении и командах

### 7.1. Строки подключения

Read preference задаётся отдельным клиентом (пулом соединений) для каждого класса операций:

```
# Класс A — primary (по умолчанию)
mongodb://mongos_router:27020/shop?readPreference=primary&readConcernLevel=majority&w=majority

# Класс B — каталог, карточки, история заказов
mongodb://mongos_router:27020/shop?readPreference=secondaryPreferred&maxStalenessSeconds=90&w=majority

# Класс C — аналитика
mongodb://mongos_router:27020/shop?readPreference=secondary&maxStalenessSeconds=900
```

### 7.2. mongosh

В mongosh `maxStalenessSeconds` передаётся опцией `readPreference` метода `find()` (или в строке подключения).
Третий аргумент `cursor.readPref()` — это параметры hedged reads, `maxStalenessSeconds` туда передать нельзя.

```javascript
use shop

const SECONDARY_90 = { readPreference: { mode: "secondaryPreferred", maxStalenessSeconds: 90 } }

// Каталог — secondary, не старше 90 с
db.products.find({ category: "electronics", price: { $lte: NumberDecimal("50000") } }, {}, SECONDARY_90)

// Карточка товара — secondary
db.products.find({ _id: productId }, {}, SECONDARY_90)

// Статус заказа — primary, только подтверждённые большинством данные
db.orders.find({ _id: orderId, customer_id: "c-102938" }, { status: 1 })
  .readPref("primary").readConcern("majority")

// Текущая корзина — primary
db.carts.find({ owner_id: "u:c-102938", status: "active" }).readPref("primary")

// Аналитика — только secondary
db.orders.aggregate(
  [{ $group: { _id: "$geo_zone", revenue: { $sum: "$total" } } }],
  { readPreference: { mode: "secondary", maxStalenessSeconds: 900 } }
)
```

### 7.3. История заказов: свои записи на SECONDARY

Причинная сессия гарантирует, что пользователь увидит только что созданный заказ, даже если читает с SECONDARY:

```javascript
const session = db.getMongo().startSession({ causalConsistency: true });
const orders = session.getDatabase("shop").orders;

// Запись — на PRIMARY, подтверждение большинством
orders.insertOne(
  { customer_id: "c-102938", created_at: new Date(), items: [], status: "created", total: NumberDecimal("0"), geo_zone: "msk" },
  { writeConcern: { w: "majority" } }
);

// Чтение — с SECONDARY, но не раньше, чем он применит запись выше
orders.find(
  { customer_id: "c-102938" },
  {},
  { readPreference: { mode: "secondaryPreferred", maxStalenessSeconds: 90 }, readConcern: { level: "majority" } }
).sort({ created_at: -1 });

session.endSession();
```

В приложении сессия привязывается к пользователю (например, `operationTime` последней записи хранится
в его HTTP-сессии и передаётся в `afterClusterTime` следующего чтения).

### 7.4. Проверка

Команды этого раздела проверены на кластере из задания 3 (MongoDB 9.0). Через `explain()` видно, какой узел
обслужил запрос:

```javascript
db.products.find({ category: "electronics" }, {}, SECONDARY_90).explain()
  .queryPlanner.winningPlan.shards.map(s => s.shardName + "@" + s.serverInfo.host)
```

| Запрос | Узлы, обслужившие запрос |
|---|---|
| `secondaryPreferred`, `maxStalenessSeconds: 90` | `shard1-2`, `shard2-3` — SECONDARY |
| `primary` | `shard1-1`, `shard2-1` — PRIMARY |
| `maxStalenessSeconds: 30` | ошибка `maxStalenessSeconds value cannot be less than 90` |
| Причинная сессия: запись, затем чтение с SECONDARY | только что созданный заказ присутствует в результате |

### 7.5. Узел для аналитики

Чтобы отчёты не влияли на SECONDARY, обслуживающие пользовательские чтения, в каждый шард добавляется скрытый
узел. Он не участвует в выборах и не получает обычных чтений, а аналитика подключается к нему напрямую:

```javascript
// На PRIMARY шарда
rs.add({ host: "shard1-analytics:27018", priority: 0, hidden: true, votes: 0 })
```
