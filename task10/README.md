# Задание 10. Cassandra для критически важных данных

Схема таблиц — в файле [schema.cql](schema.cql). Он проверен на Cassandra 5.0 (раздел 5).

## 10.1. Какие данные переносить в Cassandra

### 10.1.1. Свойства Cassandra, важные для выбора

| Сильные стороны | Ограничения |
|---|---|
| Линейное масштабирование записи и чтения: добавили узел — выросла пропускная способность | Нет транзакций между партициями и таблицами; нет JOIN |
| Нет единственного PRIMARY: писать можно в любой узел, отказ узла не останавливает запись | Согласованность настраиваемая (eventual по умолчанию); строгая — только через кворум и LWT (Paxos), которые дорогие |
| Геораспределённость «из коробки»: несколько дата-центров, запись и чтение в локальном ДЦ (`LOCAL_QUORUM`) | Запросы — только по первичному ключу; под каждый запрос нужна своя таблица (денормализация) |
| Очень быстрая запись (append в commit log и memtable) | Счётчики (`counter`) не идемпотентны и не умеют «не уходить в минус»; условные обновления — только через LWT |
| Встроенный TTL для автоматического удаления данных | Удаления создают tombstones, которые требуют repair в пределах `gc_grace_seconds` |

Отсюда правило: в Cassandra переносятся данные с **огромным объёмом и частотой записи, доступом по ключу,
требованием доступности и геораспределённости**, для которых допустима согласованность на уровне кворума
без межсущностных транзакций. Данные, где важна атомарность нескольких сущностей (деньги, остатки),
остаются в MongoDB.

### 10.1.2. Анализ данных магазина

| Данные | Целостность | Скорость | Объём и частота записи | Доступ | Решение |
|---|---|---|---|---|---|
| **Создание заказа + списание остатков** | **критична**: заказ без списания или списание без заказа — потеря денег или продажа отсутствующего товара | важна | средняя | транзакция над несколькими документами разных коллекций | **MongoDB** (распределённая транзакция, задание 7). В Cassandra нет транзакций между партициями, а условное списание через LWT на горячем товаре даст конфликты Paxos и высокую задержку |
| **Остатки товаров** | **критична**: не уйти в минус | критична | очень высокая на пике | условный декремент | **MongoDB** (`$inc` с условием `$gte`). Счётчики Cassandra не умеют проверять условие и не идемпотентны: повтор запроса после таймаута спишет остаток дважды |
| **Каталог товаров** (описание, цена, категории) | важна | важна | низкая | поиск по категории, фильтр по цене, сортировка | **MongoDB** + кеш + CDN. Фильтрация и сортировка по разным полям — слабое место Cassandra; объём каталога небольшой |
| **Корзины** | средняя: потеря одного изменения неприятна, но не финансовая | **критична**: читаются и пишутся на каждом действии пользователя | **очень высокая**: каждое добавление/удаление; на распродаже — миллионы гостевых корзин | всегда по владельцу корзины | ✅ **Cassandra** |
| **Пользовательские сессии** | низкая: потерянная сессия = повторный вход | **критична**: проверяется на каждом запросе | **очень высокая**: создание и продление на каждом обращении | по `session_id` | ✅ **Cassandra** |
| **История заказов пользователя** | высокая: заказ не должен «пропасть» из истории | важна | растёт постоянно, данные только добавляются; чтений больше, чем записей | по клиенту, новые сверху | ✅ **Cassandra** (модель чтения) |
| **Статус заказа и журнал его изменений** | высокая: устаревший статус — повторная оплата, обращения в поддержку | важна | несколько записей на заказ | по `order_id` | ✅ **Cassandra** (модель чтения) |

### 10.1.3. Выбор

В Cassandra переносятся:

1. **Корзины** (`carts_by_owner`) — самая интенсивная запись на пользователя, рост в разы на распродаже,
   доступ строго по владельцу, встроенный TTL для брошенных корзин. Геораспределённость: покупатель
   работает с корзиной в ближайшем дата-центре с минимальной задержкой. Строгие транзакции не нужны:
   окончательная проверка состава и цены делается при оформлении заказа в MongoDB.
2. **Сессии** (`sessions`, `sessions_by_user`) — key-value с очень высокой частотой записи и коротким TTL.
   Отказ одного узла не должен «разлогинить» пользователей — Cassandra продолжает принимать запись.
3. **История заказов и статусы** (`orders_by_customer`, `order_status`, `order_status_history`) — растущий
   без ограничений объём данных «только на добавление», который читается по клиенту или по заказу.
   Источник истины для создания заказа остаётся в MongoDB: заказ создаётся транзакцией вместе со списанием
   остатков, а затем через change streams MongoDB попадает в Cassandra. История и статусы читаются
   из Cassandra в любом регионе, а коллекция `orders` в MongoDB хранит только оперативные заказы
   (например, последние 90 дней) и не растёт бесконечно.

```
              создание заказа и списание остатков (транзакция)
 приложение ─────────────────────────────────────────────► MongoDB (orders, products)
     │                                                        │ change stream
     │  корзины, сессии                                       ▼
     ├───────────────────────────► Cassandra ◄──────── проектор событий заказов
     │  история заказов, статусы        ▲              (идемпотентные upsert)
     └──────────────────────────────────┘
```

Проектор идемпотентен: каждая запись в Cassandra — upsert по первичному ключу с временем события
(`USING TIMESTAMP`), поэтому повторная доставка или нарушенный порядок событий не портят данные — побеждает
более позднее изменение.

## 10.2. Концептуальная модель

### 10.2.1. Топология кластера

```sql
CREATE KEYSPACE shop
  WITH replication = { 'class': 'NetworkTopologyStrategy', 'msk': 3, 'ekb': 3 };
```

- Два дата-центра по регионам (`msk`, `ekb`), в каждом три реплики. Новые регионы добавляются как новые ДЦ.
- Приложение пишет и читает с `LOCAL_QUORUM` (2 из 3 реплик в своём ДЦ): запросы не ждут межрегиональной сети,
  а отказ любого узла в ДЦ не влияет на работу. Межрегиональная репликация — асинхронная.
- Партиционер `Murmur3Partitioner` (по умолчанию): партиция попадает на узел по хешу partition key.
- Виртуальные узлы: `num_tokens: 16` и `allocate_tokens_for_local_replication_factor: 3` в `cassandra.yaml`.

### 10.2.2. Сущности и ключи

| Таблица | Partition key | Clustering key | Основные запросы |
|---|---|---|---|
| `carts_by_owner` | `owner_id` (`u:<user_id>` / `s:<session_id>`) | `product_id` | корзина владельца; добавить, изменить, удалить товар; слияние |
| `sessions` | `session_id` | — | проверка сессии на каждом запросе; продление; выход |
| `sessions_by_user` | `user_id` | `session_id` | все сессии пользователя: «выйти на всех устройствах» |
| `orders_by_customer` | `(customer_id, year)` | `created_at DESC, order_id` | история заказов клиента, новые сверху, с постраничной выдачей |
| `order_status` | `order_id` | — | текущий статус заказа |
| `order_status_history` | `order_id` | `changed_at DESC` (timeuuid) | журнал изменений статуса |

Полные определения — в [schema.cql](schema.cql). Ниже — модель каждой сущности и обоснование ключей.

#### Корзины — `carts_by_owner`

```sql
CREATE TABLE carts_by_owner (
  owner_id    text,
  product_id  uuid,
  quantity    int,
  added_at    timestamp,
  cart_id     uuid      STATIC,
  user_id     text      STATIC,
  session_id  text      STATIC,
  created_at  timestamp STATIC,
  updated_at  timestamp STATIC,
  PRIMARY KEY ((owner_id), product_id)
) WITH default_time_to_live = 604800 AND gc_grace_seconds = 172800;
```

- **Partition key `owner_id`** — вся корзина в одной партиции: получение корзины — чтение одной партиции
  с одной группы реплик. Поле объединяет гостей и пользователей (как в задании 7), поэтому оба поиска —
  `{ session_id }` и `{ user_id }` — идут по ключу. Миллионы владельцев равномерно распределяются хешем.
- **Clustering key `product_id`** — одна строка на товар. Добавление и изменение количества — upsert одной строки,
  удаление — удаление одной строки. Нет чтения-изменения-записи всего списка и конфликтов между параллельными
  изменениями разных товаров (две вкладки браузера).
- **Static-колонки** (`cart_id`, `user_id`, `updated_at` …) хранятся один раз на партицию — это общие поля корзины.
- **Статус** «active / ordered / abandoned» не хранится: активная корзина — это существующая партиция.
  После оформления заказа или слияния партиция удаляется (состав заказа уже сохранён в MongoDB), брошенные
  корзины удаляет TTL. Так не копятся неактивные корзины и не нужен вторичный индекс по статусу.
- **TTL 7 дней** — каждая запись продлевает срок жизни своей строки.

```sql
-- Получить корзину
SELECT product_id, quantity, updated_at FROM carts_by_owner WHERE owner_id = 's:9f8e7d6c';

-- Добавить товар или изменить количество
UPDATE carts_by_owner USING TTL 604800
  SET quantity = 2, added_at = toTimestamp(now()), updated_at = toTimestamp(now())
  WHERE owner_id = 's:9f8e7d6c' AND product_id = 5f0c4a52-1c8e-4b8b-9a51-0d6f3c1e2a01;

-- Удалить товар
DELETE FROM carts_by_owner WHERE owner_id = 's:9f8e7d6c' AND product_id = 5f0c4a52-1c8e-4b8b-9a51-0d6f3c1e2a01;

-- Слияние гостевой корзины в пользовательскую: приложение читает гостевую корзину,
-- суммирует количества с пользовательской и записывает результат одним logged batch
BEGIN BATCH
  UPDATE carts_by_owner USING TTL 604800 SET quantity = 3, updated_at = toTimestamp(now())
    WHERE owner_id = 'u:c-102938' AND product_id = 5f0c4a52-1c8e-4b8b-9a51-0d6f3c1e2a01;
  DELETE FROM carts_by_owner WHERE owner_id = 's:9f8e7d6c';
APPLY BATCH;
```

Logged batch гарантирует, что обе части слияния рано или поздно будут применены (batchlog), хотя
и не изолирует их от параллельных чтений. Для корзины этого достаточно.

#### Сессии — `sessions`, `sessions_by_user`

```sql
CREATE TABLE sessions (
  session_id text, user_id text, created_at timestamp, last_seen timestamp,
  revoked boolean, geo_zone text, attributes map<text, text>,
  PRIMARY KEY ((session_id))
) WITH default_time_to_live = 1800;
```

- **Partition key `session_id`** — случайный токен высокой энтропии: идеальное распределение, каждая проверка
  сессии — точечное чтение одной строки.
- **TTL 30 минут**, продлевается при каждом обращении (`UPDATE … USING TTL 1800 SET last_seen = …`).
- **Выход — флаг `revoked = true`, а не `DELETE`.** Удаление создаёт tombstone; если реплика пропустит его и
  repair не успеет за `gc_grace_seconds`, удалённая сессия «воскреснет» — это дыра в безопасности.
  Обновление флага разрешается по времени записи без tombstones, а строка исчезнет сама по TTL.
- `sessions_by_user` — вторая таблица под запрос «все сессии пользователя». Партиция пользователя небольшая:
  сессий у одного пользователя единицы.

```sql
-- Проверка сессии
SELECT user_id, revoked, last_seen FROM sessions WHERE session_id = 'a1b2c3d4e5f6';

-- Продление
UPDATE sessions USING TTL 1800 SET last_seen = toTimestamp(now()) WHERE session_id = 'a1b2c3d4e5f6';

-- Выход
UPDATE sessions USING TTL 1800 SET revoked = true WHERE session_id = 'a1b2c3d4e5f6';
```

#### История заказов — `orders_by_customer`

```sql
CREATE TABLE orders_by_customer (
  customer_id text, year smallint, created_at timestamp, order_id uuid,
  status text, total decimal, geo_zone text,
  items frozen<list<frozen<order_item>>>, updated_at timestamp,
  PRIMARY KEY ((customer_id, year), created_at, order_id)
) WITH CLUSTERING ORDER BY (created_at DESC, order_id ASC);
```

- **Partition key `(customer_id, year)`** — история клиента в его партиции. Год ограничивает размер партиции:
  даже у оптового покупателя с тысячами заказов в год партиция остаётся в рекомендуемых пределах
  (до ~100 МБ и ~100 тыс. строк), а у розничного — единицы строк. Без года партиция активного клиента росла бы бесконечно.
- **Clustering key `created_at DESC, order_id`** — заказы хранятся отсортированными, новые сверху: «последние
  20 заказов» — чтение начала одной партиции без сортировки. `order_id` делает ключ уникальным, если два заказа
  созданы в одну миллисекунду.
- **Позиции заказа** — `frozen<list<frozen<order_item>>>`: состав заказа не меняется после создания, поэтому
  хранится одним значением рядом с заказом. Карточке списка не нужны другие таблицы.

```sql
-- Последние заказы клиента за текущий год
SELECT order_id, created_at, status, total FROM orders_by_customer
  WHERE customer_id = 'c-102938' AND year = 2026 LIMIT 20;

-- Следующая страница: заказы раньше последнего показанного
SELECT order_id, created_at, status, total FROM orders_by_customer
  WHERE customer_id = 'c-102938' AND year = 2026 AND created_at < '2026-11-01 00:00:00+0000' LIMIT 20;
```

Приложение читает партиции по годам от текущего к прошлым, пока не наберёт страницу.

#### Статус заказа — `order_status`, `order_status_history`

- **`order_status`, partition key `order_id`** — текущий статус: точечное чтение для страницы заказа и
  поддержки. `order_id` — UUID, распределение равномерное.
- **`order_status_history`, partition key `order_id`, clustering key `changed_at` (timeuuid, DESC)** — журнал
  изменений: только добавление строк, без перезаписи. Партиция заказа маленькая (десяток событий).
- При смене статуса проектор пишет в три таблицы — `order_status`, `order_status_history` и строку заказа
  в `orders_by_customer` — одним logged batch с временем события:

```sql
BEGIN BATCH USING TIMESTAMP 1795000000000000
  UPDATE order_status SET status = 'paid', updated_at = '2026-11-27 10:20:00+0000'
    WHERE order_id = 0b8f9c2e-6a1d-4c3b-8e5f-2a9d7c4b1e30;
  INSERT INTO order_status_history (order_id, changed_at, status, source)
    VALUES (0b8f9c2e-6a1d-4c3b-8e5f-2a9d7c4b1e30, 50554d6e-29bb-11e5-b345-feff819cdc9f, 'paid', 'payment');
  UPDATE orders_by_customer SET status = 'paid', updated_at = '2026-11-27 10:20:00+0000'
    WHERE customer_id = 'c-102938' AND year = 2026
      AND created_at = '2026-11-27 10:15:00+0000' AND order_id = 0b8f9c2e-6a1d-4c3b-8e5f-2a9d7c4b1e30;
APPLY BATCH;

-- Статус заказа
SELECT status, updated_at FROM order_status WHERE order_id = 0b8f9c2e-6a1d-4c3b-8e5f-2a9d7c4b1e30;
-- Журнал
SELECT changed_at, status, source FROM order_status_history WHERE order_id = 0b8f9c2e-6a1d-4c3b-8e5f-2a9d7c4b1e30;
```

`USING TIMESTAMP` = время события в MongoDB: если события придут не по порядку, более раннее не перезапишет
более позднее.

### 10.2.3. Горячие партиции

Горячая партиция в Cassandra — та, на которую приходится непропорционально много запросов. Все её реплики
(3 узла в ДЦ) перегружаются, и добавление узлов не помогает — партиция не делится.

| Таблица | Риск | Почему партиция не станет горячей |
|---|---|---|
| `carts_by_owner` | всплеск гостевых корзин на распродаже | партиция = одна корзина; нагрузка — сумма миллионов маленьких независимых партиций, хеш распределяет их по всем узлам. Один пользователь физически не создаст нагрузку, опасную для партиции |
| `sessions` | все проверки сессий | ключ — случайный токен; каждая партиция — одна строка |
| `orders_by_customer` | очень активный клиент (оптовик) | год ограничивает размер партиции; частота чтения своей истории одним клиентом невысока |
| `order_status*` | массовое обновление статусов | партиция = один заказ |

Чего модель сознательно избегает:

- **Партиционирования по времени** (`orders_by_day`, `carts_by_date`): все записи текущего дня попали бы
  в одну партицию на одном наборе реплик — классическая горячая партиция. Если такая выборка нужна
  для аналитики, используется **бакетирование**: `PRIMARY KEY ((day, bucket), created_at, order_id)`, где
  `bucket = hash(order_id) % 32` — запись дня распределяется на 32 партиции.
- **Партиционирования по товару или категории** (`carts_by_product`, `orders_by_category`): «Электроника»
  на распродаже — та самая горячая категория из задания 8.
- **Низкокардинальных ключей** (`status`, `geo_zone`) — несколько огромных партиций.

### 10.2.4. Изменение топологии без решардинга

В MongoDB при смене ключа или росте горячей категории нужны split, перенос чанков и решардинг (задание 8).
В Cassandra этого нет:

- **Консистентное хеширование.** Расположение партиции определяется хешем partition key на кольце токенов.
  При добавлении узла он забирает часть диапазонов токенов у соседей, а ключи не пересчитываются и данные
  не перераспределяются по всему кластеру.
- **Виртуальные узлы** (`num_tokens: 16` с `allocate_tokens_for_local_replication_factor: 3`): каждый узел
  владеет многими небольшими диапазонами. Новый узел получает данные понемногу со многих узлов, а не целиком
  с одного соседа; удаление узла распределяет его данные по многим оставшимся. Это ускоряет bootstrap и не
  создаёт перегрузки на одном узле.
- **Нет чанков и балансировщика.** Партиции маленькие и многочисленные, поэтому равномерность достигается
  самим хешированием. Поскольку модель не допускает огромных или горячих партиций, нет и ситуации,
  когда данные «не делятся».
- **Новый регион** добавляется как новый дата-центр в `replication` keyspace и наполняется командой
  `nodetool rebuild -- msk`, не затрагивая работу существующих ДЦ.

```shell
# Добавление узла: auto_bootstrap: true в cassandra.yaml, затем после запуска на старых узлах
nodetool cleanup shop        # удалить данные, которые теперь принадлежат новому узлу

# Новый дата-центр
cqlsh -e "ALTER KEYSPACE shop WITH replication = {'class': 'NetworkTopologyStrategy', 'msk': 3, 'ekb': 3, 'nsk': 3};"
nodetool rebuild -- msk      # на каждом узле нового ДЦ
```

Ключи выбираются один раз под запросы и не зависят от числа узлов — смена топологии не требует менять модель.

## 10.3. Стратегии восстановления целостности

### 10.3.1. Механизмы

| Механизм | Как работает | Что гарантирует | Цена |
|---|---|---|---|
| **Hinted Handoff** | Если реплика недоступна при записи, координатор сохраняет «подсказку» (hint) и доставляет её, когда реплика вернётся. Хранится не дольше `max_hint_window` (по умолчанию 3 ч) | быстро догоняет реплику после кратковременного отказа; повышает доступность записи | почти бесплатно для запроса; не гарантия — hint теряется, если упал сам координатор или окно истекло |
| **Read Repair** | При чтении с уровнем выше `ONE` координатор сравнивает ответы реплик; если они расходятся, дописывает актуальные данные на отставшие реплики. `read_repair = 'BLOCKING'` — ответ клиенту ждёт исправления; `'NONE'` — исправления нет | монотонные кворумные чтения: прочитанное с `QUORUM` значение не «откатится» при следующем чтении | добавляет задержку к чтениям, на которых найдено расхождение; исправляет только читаемые данные |
| **Anti-Entropy Repair** (`nodetool repair`, Cassandra Reaper) | Реплики строят деревья Меркла по диапазонам токенов, сравнивают их и передают различающиеся данные. Полный или инкрементальный (только новые данные) | полная согласованность всех реплик, включая данные, которые никто не читает; распространение tombstones до истечения `gc_grace_seconds` (иначе удалённые данные «воскресают») | фоновая нагрузка на CPU, диск и сеть; запускается по расписанию вне пика |

Компромисс задают уровни согласованности: при `W + R > RF` (например, `LOCAL_QUORUM` на запись и чтение,
2 + 2 > 3) чтение всегда видит последнюю подтверждённую запись, но ждёт ответа двух реплик.
Уровень `LOCAL_ONE` быстрее, но может вернуть устаревшие данные. Чем ниже уровень согласованности запросов,
тем больше работы ложится на механизмы восстановления.

### 10.3.2. Выбор для каждой сущности

| Сущность | Запись / чтение | Hinted Handoff | Read Repair | Anti-Entropy Repair |
|---|---|---|---|---|
| **Корзины** `carts_by_owner` | `LOCAL_QUORUM` / `LOCAL_QUORUM` | ✅ включён | ✅ `BLOCKING` | ✅ инкрементальный ежедневно, `gc_grace_seconds` = 2 дня |
| **Сессии** `sessions`, `sessions_by_user` | `LOCAL_QUORUM` / `LOCAL_ONE` | ✅ включён | ❌ `NONE` | ❌ не нужен |
| **История заказов** `orders_by_customer` | `LOCAL_QUORUM` / `LOCAL_QUORUM` | ✅ включён | ✅ `BLOCKING` | ✅ инкрементальный ежедневно + полный еженедельно |
| **Статус заказа** `order_status`, `order_status_history` | `LOCAL_QUORUM` (+ `EACH_QUORUM` для финальных статусов) / `LOCAL_QUORUM` | ✅ включён | ✅ `BLOCKING` | ✅ инкрементальный ежедневно + полный еженедельно |

#### Корзины: все три механизма

- **Hinted Handoff** — основной механизм. Корзина пишется на каждом действии пользователя; кратковременный отказ
  узла (перезапуск, обновление) не должен терять добавленные товары. Hints восстанавливают реплику
  за секунды после её возвращения, без затрат на запрос.
- **Read Repair `BLOCKING`** — корзину читают сразу после изменения с `LOCAL_QUORUM`. Блокирующий read repair
  гарантирует, что пользователь не увидит, как товар «появился, исчез и снова появился» при чтении с разных
  реплик. Задержка добавляется только к редким чтениям с расхождением.
- **Anti-Entropy Repair ежедневно** — корзины удаляют товары (`DELETE`) и целиком удаляются после заказа или
  слияния. Без repair в пределах `gc_grace_seconds` реплика, пропустившая удаление, «воскресит» удалённый
  товар в корзине. `gc_grace_seconds` уменьшен до 2 дней (корзина живёт неделю), поэтому repair
  обязателен не реже раза в 2 дня — с запасом выбран ежедневный инкрементальный.

#### Сессии: только Hinted Handoff

- **Скорость важнее строгой согласованности.** Сессия проверяется на каждом запросе, поэтому чтение — `LOCAL_ONE`
  с минимальной задержкой. Запись — `LOCAL_QUORUM`, чтобы новая сессия сразу была на большинстве реплик.
- **Read Repair `NONE`** — блокирующий read repair на самой частой операции добавил бы задержку, а для данных,
  живущих 30 минут, выгода мала. Расхождение реплик чаще всего означает разницу в `last_seen` на секунды.
- **Anti-Entropy Repair не нужен.** Все данные имеют TTL 30 минут и истекают на всех репликах одинаково;
  явных удалений нет (выход — флаг `revoked`), поэтому нет tombstones, которые могли бы «воскреснуть».
  Repair сравнивал бы данные, которые всё равно исчезнут быстрее, чем он закончится. Поэтому таблицы исключаются
  из расписания repair, а `gc_grace_seconds` уменьшен до часа.
- **Hinted Handoff** закрывает кратковременные отказы узла. Если сессия всё же не найдена на реплике (`LOCAL_ONE`
  попал на отставшую реплику), приложение повторяет чтение с `LOCAL_QUORUM`, прежде чем отправить
  пользователя на повторный вход.

#### История заказов и статусы: все три механизма, максимальные гарантии

- **Read Repair `BLOCKING`** — пользователь, увидевший статус «оплачен», не должен при следующем открытии
  страницы увидеть «ожидает оплаты». Монотонные кворумные чтения закрывают именно этот риск;
  задержка read repair допустима — страница заказа открывается редко по сравнению с корзиной и сессиями.
- **Anti-Entropy Repair: инкрементальный ежедневно, полный еженедельно** — старые заказы читают редко,
  поэтому read repair их не исправит. Только плановый repair гарантирует, что все реплики истории
  совпадают, даже если реплика была недоступна дольше окна hints (3 ч). `gc_grace_seconds` — стандартные
  10 дней, а еженедельный полный repair укладывается в этот интервал с запасом.
- **Hinted Handoff** — ускоряет восстановление после кратких отказов.
- **Финальные статусы** (`paid`, `cancelled`, `refunded`) записываются с `EACH_QUORUM` — подтверждение
  кворума в каждом дата-центре. Пользователь, перешедший из одного региона в другой, не увидит устаревший
  статус оплаты. Это дороже по задержке (ожидание межрегиональной сети), но таких записей мало.
- **Повторная доставка из MongoDB.** Источник истины — MongoDB, поэтому при сомнении в целостности истории
  проектор может переиграть события change stream с нужного момента. Запись идемпотентна (`USING TIMESTAMP`).

### 10.3.3. Настройки

`cassandra.yaml` (на всех узлах):

```yaml
hinted_handoff_enabled: true
max_hint_window: 3h            # дольше — узел восстанавливается через repair
hinted_handoff_throttle: 1024KiB
max_hints_delivery_threads: 2
num_tokens: 16
allocate_tokens_for_local_replication_factor: 3
```

Расписание repair (Cassandra Reaper или cron):

```shell
# Ежедневно, ночью: инкрементальный repair основного диапазона каждого узла — корзины, заказы, статусы
nodetool repair -pr shop carts_by_owner orders_by_customer order_status order_status_history

# Еженедельно: полный repair истории заказов и статусов
nodetool repair -pr -full shop orders_by_customer order_status order_status_history

# Сессии в расписание не входят
```

Уровни согласованности задаются в приложении (пример для драйвера Python):

```python
from cassandra import ConsistencyLevel
from cassandra.query import SimpleStatement

get_cart = SimpleStatement(
    "SELECT product_id, quantity FROM carts_by_owner WHERE owner_id = %s",
    consistency_level=ConsistencyLevel.LOCAL_QUORUM)

check_session = SimpleStatement(
    "SELECT user_id, revoked FROM sessions WHERE session_id = %s",
    consistency_level=ConsistencyLevel.LOCAL_ONE)

final_status = SimpleStatement(
    "UPDATE order_status SET status = %s, updated_at = %s WHERE order_id = %s",
    consistency_level=ConsistencyLevel.EACH_QUORUM)
```

В cqlsh: `CONSISTENCY LOCAL_QUORUM;`.

### 10.3.4. Итог: latency против гарантий

| Сущность | Приоритет | Что жертвуем | Механизмы |
|---|---|---|---|
| Сессии | минимальная задержка на каждом запросе | строгая согласованность (редкое повторное чтение или вход) | Hinted Handoff |
| Корзины | быстрый отклик и отсутствие «прыгающих» товаров | небольшая задержка на чтениях с расхождением, фоновая нагрузка repair | Hinted Handoff + Read Repair + ежедневный repair |
| История заказов и статусы | гарантия, что заказ и статус не пропадут и не откатятся | задержка кворумных чтений, межрегиональное подтверждение финальных статусов, регулярный полный repair | Hinted Handoff + Read Repair + ежедневный и еженедельный repair + переигрывание из MongoDB |

- параметры `cassandra.yaml` из раздела 10.3.3 совпадают с именами в Cassandra 5.0, команды `nodetool repair`
